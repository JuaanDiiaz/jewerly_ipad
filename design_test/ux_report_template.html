Design review · P&A Jewelry inventory app

UX Audit & Improvement Roadmap

A whole-app pass over the Flutter client: what works, what broke, and a priority order for fixing it. Every finding was verified against the running app and the source, and the screenshots below were taken from the live build during this review.

Scope · all 20+ screens  |  Build · Windows debug vs dev API  |  Evidence · 4 captures from the live app

The short version. The app's information design is solid — consistent CRUD patterns, a coherent jewelry identity, and the new Reports dashboard set a good standard. Three things hold the UI back: theme switching is genuinely broken and its causes touch 28 files, the app is motionless (no screen transitions, no feedback between save and pop), and a handful of screens ignore the theme system entirely, showing baked-in light colors after dark mode.

1 · The theme toggle bug, explained

This is the defect you noticed by hand: switch Dark, and parts of the app go dark while parts stay cream. The screenshots show it live — same moment, one screen, two palettes.

Three causes stack

P0A const widget freezes the whole screen at its last build

main.dart:91 — child: const HomeScreen(). const tells Flutter the widget instance never changes, so when the MaterialApp theme flips, the compiler reuses the existing HomeScreen element without rebuilding it. Every descendant keeps its old colors. One removed keyword starts the fix.

P0The screen cache holds every visited screen in its last palette

HomeScreen keeps visited pages alive in an IndexedStack (home_screen.dart:18, 214). Even after the const fix, a widget rebuilt only when its provider notifies shows the old theme until re-navigation — which the tests demonstrated directly.

P0Two competing color sources disagree

AppTheme exposes adaptive getters (background, surfaceColor, textColor…) from a static _isDark flag, while the Material side derives from Theme.of(context). Static getters subscribe to nothing, so widgets built on them don't invalidate when the flag turns. The fix is one source of truth; the 28-file cleanup below does it file by file.

P128 files bypass the theme entirely

A grep counts 231 hardcoded-mode colors across 28 files. Worst offenders: sale_screen.dart (46 — white sale panels), physical_count_main_screen.dart (34), modern_sidebar.dart (19), purchases_main_screen.dart (13). Dark Reports is the visible symptom: the selected report chip (lightGold background, light text) becomes unreadable precisely because a light-only chip color leaked in.

2 · Motion, feedback, dialogs

P1Screens swap with zero transition

Clicking a sidebar item does a bare setState inside the IndexedStack — content teleports. Adding an AnimatedSwitcher (180 ms fade + small slide-up) around the content pane, plus a pageTransitionsTheme for modal routes, is a contained change in two files.

P1Save flows pop before the result is known

Products, Categories, and Purchases close the form dialog at the moment of submit and then show success or failure as a bare snack bar. The pattern hides failures until you've left the form, and the duplicate "Product saved" snack bars in products_main_screen.dart:629–645 stack on top of it. Fix: keep the dialog open while saving, disable the action button, and pop only on success with the snackbar after.

P1Several screens fail silently

When a delete or save throws, the screen just re-fetches and sits there. The standard is already in the codebase — errorSnackBar/successSnackBar — but a few screens never call it on the failure path.

P2Hover states are the only interaction feedback

Mouse hover works everywhere, but on touch (the iPad target) the same affordances read as dead tiles. A pressed-state ripple or scale on sidebar items and cards covers the tablet case.

3 · Layout & information design

P2Loading states are inconsistent two ways

The Reports screen uses the shared BaseScreen with skeletons; Customers has its own SkeletonList; Products, Sales, Inventory show bare spinners. Two components already exist — adopting them everywhere is a standardization pass, not new design work. One detail found while auditing: Products' grid is hardcoded to 3 columns; Wrap or a width-aware SliverGrid would let it breathe on iPad's wider canvas.

P2Keyboard handling is one-screen-only

Only the Customers sheet applies viewInsets. On other forms the keyboard covers the field being edited — a real issue on iPad where the soft keyboard takes 40% of the screen.

P2Settings sells features the app doesn't have

Notifications toggle, Clear Cache, Language, Export, Import, Help, and Report Bug all respond with "coming soon" or are decorative. They teach the user to stop trusting the screen. Recommend hiding them under a "Coming soon" section header or removing them until real.

P2Dead code weighs the audit down

bottom_bar_screen.dart and LoadingProvider are unreachable (the sidebar replaced the bottom bar months ago). Removing them shrinks the surface the next audit has to read.

5 · How design gets tested from here

Three layers, cheapest first.

  • Screenshot review (worked in this session). The app runs against the dev API; a PowerShell helper drove it — design_test/click.ps1 restores, brings the window forward, injects synthetic taps and wheel scrolls, and captures the window as a PNG. That loop is how the theme bug was caught and confirmed. It's Windows-desktop-only; once you have Apple hardware or CI with macOS, the same capture works via xcrun simctl io booted screenshot.
  • Golden tests in CI. Flutter supports matchesGoldenFile: render a key widget (Reports dashboard, sidebar, a form dialog) in both Brightness.light and Brightness.dark, and CI fails the moment a screenshot diverges from the committed reference. That makes "dark mode is broken" a red build instead of a discovered bug — directly targeting defect class #1.
  • Integration test drive. flutter test integration_test with the mock API exercises toggle→visit→toggle and verifies no light tokens survive on dark screens. Add it alongside the existing smoke test once P0 lands.
